# Asset generation

The Assets workspace uses a prompt and a supported type. Names are generated by an
OpenAI Responses request before media inference (or alongside generated text); users can rename completed local
assets without changing their original bytes. Upload names remain optional.

`GET /asset-generation?gameId=GAME&view=options` is the authoritative generator
contract. It returns available types, models, styles, required inputs and defaults.
The browser does not infer that an arbitrary asset type has a generation provider.
Local development supports images (including maps, blueprints, locations and
character portraits), videos, narration and text when their API workers are healthy.
The hosted broker currently supports image generation; it does not advertise
standalone video, narration or text jobs that its workers cannot execute.

Hosted image model choices are `gpt-image-1`, `gpt-image-1.5` and `gpt-image-1-mini`.
Local Generate Asset additionally discovers active fal text-to-image models through the
read-only catalog API. It offers every executable prompt-based image contract with
provider-default inputs and one downloadable image result. Models requiring an initial
image, extra credentials or other unsupported required inputs are excluded rather than
advertised as working. Large model lists use a searchable shadcn combobox.

The image worker stores a complete versioned catalog in the local database, separate
from processor heartbeats, and refreshes it every six hours. A selected job pins the
endpoint, schema hash, explicit standard defaults and provider price evidence; later
catalog changes cannot alter queued generation. Catalog/pricing discovery is read-only.
Model controls display estimated provider unit prices, OpenAI medium-image output
rates, video profile estimates per eight seconds and speech credits per thousand
characters where known. These are estimates, not reconciled billed charges; settings,
input tokens, titles and subscription allocation can affect actual costs.

fal requests checkpoint dispatch intent before submission, retain the provider request
identity and poll only validated queue URLs. Unknown POST outcomes never automatically
resubmit; existing complete receipts publish without another inference. Original PNG,
JPEG or WebP bytes and exact request/response lineage remain immutable. The selected
model endpoint and actual fal request ID are retained in generation provenance.
The configured default remains `gpt-image-1`. Visual styles use the game's default
unless explicitly selected. Local video offers the established fal model profiles,
with a pinned same-game starting image for image-to-video models. Narration uses
Eleven v3 and actual configured voices, preserving the prompt as the words to speak.
Text uses the configured editorial API model. No model is silently substituted.

`POST /asset-generation` accepts `{gameId,type,prompt,operationId}` with applicable
`model`, `style`, `characterId` and local media `inputs`. Historical producers
may supply an explicit name. New hosted requests use schema version 2. Repeating an
operation returns the same job; changing its inputs under that operation fails.
`GET /asset-generation` requires `gameId`, optionally `jobId`; without an ID it
returns bounded same-game job pages and a scoped cursor. Reloading retains progress.
The browser never receives provider credentials or treats queued work as completion.

## Hosted image worker

```sh
panther assets worker --work-dir /private/path/asset-generation --once
panther assets worker --work-dir /private/path/asset-generation
panther assets worker --work-dir /private/path/asset-generation --resume-job JOB_ID
```

Sign in to Panther and configure a server-side `OPENAI_API_KEY` in the worker's
environment. The broker leases queued jobs to a configured worker. AWS stores job
state; the laptop worker calls OpenAI APIs directly. It does not invoke Codex for
new image generation. See [local development](local-development.md) for the separate
SQLite worker supervisor and private `.env` setup.

Requests are checkpointed before inference and complete provider responses retained
outside Git. Unknown outcomes stop rather than repeating a paid call. Once output
exists, resuming reuses that exact PNG and retries publication only. Historical
successful tool outputs retain their actual subscription provenance; unknown old
checkpoints are never converted into fresh API submissions. A separately explicit
Generate action creates a new operation. No automatic paid retries or credit
purchases exist.

The worker rejects symlinks, malformed PNGs, incorrect CRCs and excessive dimensions.
It uploads through the supported Panther CLI without overwriting originals. The
image has current semantic version metadata and its full request in hidden
`generation-provenance` JSON, linked by immutable `sourceKeys`. Actual provider,
model, title-generation evidence and unknown billed cost are preserved. A provider
response is not evidence of a billed amount; unknown never means zero.

Publication requires verified immutable bytes, explicit job/type/model metadata and
actual SHA-256. It does not wait for the asynchronous materialized browse projection.
No storage scan or static sample dataset populates the library. Previous assets and
their original metadata are preserved without invented generation history.

Portrait requests require an initialized same-game character. The broker pins the
structured revision and facts in `characterReference`; operation reuse preserves
that snapshot. Any generated or uploaded character asset carries an explicit same-game
character association. Generic generation leaves the profile portrait unchanged.
The profile portrait control submits `selectAsPortrait: true`; completion atomically
publishes the job, selects the verified image at the pinned character revision, and
appends recoverable character history. A concurrent profile edit preserves that edit
and saves the image in Assets without changing the portrait. Existing reference pins
remain guarded and retained. Named physical appearances and artwork selections remain
separate from this profile thumbnail; generation does not invent appearance/story facts.
The shared creation dialog closes after submission; progress stays beside the portrait
or inside Assets and restores from bounded, character-filtered jobs after navigation.

Production route changes require CDK deployment and a running authenticated worker.
An offline worker leaves work queued honestly. Local capability checks disable
unavailable generators and retain terminal failures with useful recovery.

## User tags

Settings manages the current game vocabulary through Add Tag, Rename and Delete.
`POST /tags/manage` accepts a guarded operation ID and a rename or delete action.
Changes update current catalog labels across existing assets without editing source
bytes, manuscript text or historical generation metadata. Schema-versioned tag-change
records retain the prior label and change time. Recreating a deleted tag permits new
assignments and does not restore old assignments. Case-insensitive names are unique;
conflicting concurrent changes return a conflict instead of silently overwriting them.

The same bounded display projection applies to existing and future catalog pages in
all games. It reads the per-game metadata policy from the materialized catalog, never
scans source storage. Existing games begin with an empty policy and require no invented
backfill. Local SQLite uses the same projection and retains changes outside Git.
